# План разработки одностраничного сайта риелтора

Дата подготовки: 13 ноября 2026 года. Основание: `descr.txt` и последующие уточнения владельца проекта.

## 1. Результат и границы проекта

Создать быстрый адаптивный сайт Елены Сергеевны Левошиной, частного риелтора из Чебоксар. Основная задача — побудить посетителя позвонить; дополнительные действия — перейти в мессенджер и посмотреть актуальные объекты.

Это статический одностраничник. Контент редактируется в исходных файлах, после чего сайт пересобирается и публикуется. Админка, база данных, Python, сервер приложения, CRM и авторизация посетителей не нужны.

Результат сборки — каталог `dist/` с HTML, CSS, изображениями и небольшим количеством JavaScript. Его можно разместить на обычном статическом хостинге либо обслуживать контейнером Caddy на VPS. Node.js нужен только при разработке и сборке.

Примерно 10 объектов показываются на этой же странице. Отдельные страницы объектов, сложный поиск и личные кабинеты в первую версию не входят. Если потребуется больше фотографий, использовать раскрытие карточки или доступный диалог, сохранив основную информацию в HTML.

Последние уточнения имеют приоритет над первоначальной анкетой: самостоятельное обновление означает изменение файлов и повторную публикацию, а не интерфейс управления.

## 2. Выбранный стек

| Задача | Решение | Причина |
| --- | --- | --- |
| Сборка | Vite + официальный React-плагин | Простая разработка и сборка статических файлов |
| Интерфейс | React + TypeScript | Знакомый стек, компоненты `.tsx`, клиентский рендеринг |
| Типизация | TypeScript, `strict: true` | Проверка структуры контактов, услуг и объектов до публикации |
| Стили | Обычный CSS, CSS custom properties, Grid, Flexbox | Для одной страницы достаточно; небольшая зависимость от инструментов |
| Контент | Типизированные `.ts`-файлы и локальные изображения | Редактирование в редакторе, история Git, отсутствие базы |
| Пакеты | npm, `package-lock.json`, установка через `npm ci` | Воспроизводимость в CI и Docker |
| Среда сборки | Поддерживаемая LTS-ветка Node.js | Совместимость с выбранными версиями Vite и инструментов |
| Проверка кода | TypeScript (`tsc --noEmit`), ESLint, Prettier | Ошибки типов, качество и единое оформление |
| Проверки браузера | Playwright + axe-core, Lighthouse | Основные пользовательские сценарии, доступность и скорость |
| Раздача сайта | Caddy 2, Docker Engine + Compose v2 | Статические файлы, HTTPS, удобный перенос |
| История и публикация | Git, CI выбранного Git-хостинга | Проверяемая сборка и возврат к предыдущему выпуску |

Весь интерфейс реализуется обычными React-компонентами `.tsx`, приложение монтируется через `createRoot`. Роутер, Redux, библиотеки запросов и backend для одной страницы не нужны: навигация работает через HTML-якоря, контент импортируется из TS-файлов. Такой старт через Vite описан в [официальной документации React](https://react.dev/learn/build-a-react-app-from-scratch).

Базовый вариант — клиентский рендеринг (CSR), без SSR и обязательного предварительного рендеринга. После сборки сервер раздаёт статические файлы, а React формирует интерфейс в браузере. Это нужно учитывать при SEO и работе без JavaScript; требования приведены ниже.

### Политика версий

1. При старте выбрать актуальные стабильные совместимые версии Vite, React, TypeScript и инструментов. Не использовать preview/canary/RC.
2. Выбрать Node LTS из [официальной таблицы релизов](https://nodejs.org/en/about/previous-releases), сверить требования Vite. Зафиксировать версию в `.node-version`, `engines` и Dockerfile.
3. Зафиксировать точные зависимости и lockfile; образы Node/Caddy — по версии и digest в рабочей реализации. Не использовать плавающий `latest`.
4. Записать фактические версии и дату проверки в README. Этот план не фиксирует непроверенные будущие patch-релизы.
5. Обновлять зависимости небольшими PR/коммитами с повторной сборкой и проверками. Срочные исправления безопасности устанавливать вне обычного графика.

Дополнительный фреймворк не требуется. Сборку `dist/` можно разместить на статическом хостинге или в контейнере Caddy. Node.js работает только при сборке; [Vite preview не является production-сервером](https://vite.dev/guide/static-deploy.html).

## 3. Содержание страницы

### 3.1. Шапка

- Имя и подпись «Частный риелтор».
- Якорные ссылки «Услуги», «Объекты», «Контакты».
- Номер телефона и заметная кнопка звонка.
- На маленьком экране — компактная шапка, при необходимости доступное раскрывающееся меню.

### 3.2. Первый экран

- Один `h1`, например «Помощь с покупкой и продажей недвижимости».
- Елена Сергеевна Левошина, Чебоксары, более 20 лет в недвижимости.
- Портрет, предоставленный владельцем.
- Краткое описание личной помощи без неподтверждённых показателей.
- Основная кнопка «Позвонить» с `tel:`; рядом доступное текстовое представление номера.
- «Звонки с 10:00 до 20:00 по московскому времени».

### 3.3. Услуги — в согласованном порядке

1. Покупка и продажа недвижимости: новостройки, вторичное жильё, дома, участки и коммерческие объекты.
2. Одобрение ипотеки: помощь с подбором и подачей заявки, сопровождение; рядом пояснение, что окончательное решение принимает банк.
3. Сопровождение сделки, включая дистанционные сделки.

Стоимость: «Стоимость услуг рассчитывается индивидуально. Уточните по телефону». Указать бесплатную первичную консультацию. Не придумывать цены «от», фиксированные сроки, гарантированное одобрение или результаты.

Географию изложить коротко в существующем блоке: личная работа в Чебоксарах, Новочебоксарске и Чувашии; Москва и область — дистанционно. Возможность дистанционной помощи по России описать без обещания личного присутствия. Отдельный подробный раздел об электронных сделках не нужен.

### 3.4. Актуальные предложения

Карточка объекта содержит фото, заголовок, населённый пункт/разрешённый адрес, цену, тип недвижимости, площадь и подходящие типу характеристики. Для квартиры — комнаты и этаж; для участка — площадь участка; для коммерции — назначение. Не выводить пустые или неподходящие поля.

- Примерно 10 карточек на старте.
- Постоянный идентификатор и якорь, например `#object-flat-001`.
- Кнопка звонка и ссылка на выбранный мессенджер. В предзаполненный текст включать название/ID объекта только там, где сервис официально поддерживает такой формат.
- Для нескольких фото — дополнительная галерея с клавиатурным управлением. Не запускать автоматическую карусель.
- Проданный/снятый объект убирать из текущих предложений через `published: false`.
- Если объектов нет — честное сообщение с предложением позвонить, без пустой сетки.
- Не нужен фильтр ради 10 объявлений. Его можно добавить позднее при фактической необходимости.

### 3.5. Контакты и подвал

Телефон, часы связи по Москве, email, рабочие ссылки MAX/WhatsApp/Telegram после предоставления и проверки. Непредоставленные контакты не выводить. Показать краткую географию работы, имя специалиста и необходимые сведения владельца сайта.

Отзывы, логотипы банков, дипломы, возраст, год начала работы, вымышленные кейсы и подробный процесс работы не размещать: они не согласованы либо прямо исключены в анкете.

## 4. Обращения без серверной части

В исходной анкете есть форма заявки, но для полностью статического варианта рекомендуется заменить её на понятный блок «Связаться» со звонком и прямыми ссылками в мессенджеры. Это изменение относительно анкеты нужно зафиксировать до реализации.

Сам HTML/React не умеет безопасно доставлять заявки в мессенджер: для автоматической отправки нужен внешний обработчик или свой сервер. Токен бота, SMTP-пароль или секрет внешнего API нельзя помещать в JS, HTML, публичные env-переменные либо репозиторий.

Основной сценарий первой версии:

1. Посетитель нажимает «Позвонить» или выбирает мессенджер.
2. Открывается соответствующее приложение/веб-страница. Если приложение не установлено, остаётся видимый номер, который можно скопировать.
3. На сайте не показывается сообщение «Заявка отправлена», поскольку сайт не отправлял и не подтверждал сообщение.

`mailto:` можно использовать как дополнительный контакт, но не как гарантированный механизм доставки заявки. Не делать неработающую форму ради внешнего вида.

Если позднее форма станет обязательной, оформить отдельное расширение: обработчик, серверная валидация, ограничения частоты, защита от спама, политика хранения, согласие, обработка ошибок доставки и выбор инфраструктуры для персональных данных. Для текущего одностраничника это не требуется.

## 5. Организация исходников

Предлагаемая структура, окончательные имена можно уточнить при реализации:

```text
src/

    Contacts.tsx
    Footer.tsx
    Gallery.tsx          # только если требуется интерактивная галерея
  data/
    site.ts              # имя, контакты, часы, SEO, ссылки
    services.ts
    properties.ts
  types/content.ts
  assets/
    portrait/
    properties/
  styles/
    tokens.css
    global.css
index.html               # корневой HTML, метаданные, noscript
scripts/
  validate-content.ts
  optimize-images.mjs    # если изображения не подготовлены заранее
public/
  404.html
  favicon.svg
```

Контент отделить от разметки. `npm run check` выполняет `tsc --noEmit` и проверку контента; `npm run build` подготавливает изображения/метаданные и запускает `vite build`. В `tsconfig` включить типы `vite/client` для импортов ресурсов. В конфиге предусмотреть canonical origin сайта. Домен — публичное значение, его можно передавать на этапе сборки; изменение origin требует пересборки SEO-метаданных.

### Минимальная модель объекта

```ts
interface Property {
  id: string;
  published: boolean;
  title: string;
  kind: 'apartment' | 'house' | 'land' | 'commercial';
  locality: string;
  address?: string;
  priceRub: number;
  areaM2: number;
  rooms?: number;
  floor?: number;
  floorsTotal?: number;
  landAreaM2?: number;
  description: string;
  images: Array<{ src: string; alt: string; width: number; height: number }>;
}
```

Пути к изображениям получать через импорты ресурсов Vite либо использовать проверенные публичные URL. Обязательные характеристики проверить дополнительно при сборке: уникальность ID, положительные цена/площадь, минимум одно фото у опубликованного объекта, корректные ссылки и наличие обязательных контактов. TypeScript сам по себе не проверяет содержимое изображений и бизнес-ограничения.

Телефон хранить отдельно в машинном формате для `tel:` и в читаемом виде. Цены форматировать через `Intl.NumberFormat('ru-RU')`. Описания — текстом; не использовать произвольный HTML из контентных файлов без необходимости.

## 6. Адаптивность и доступность

Целевой ориентир — применимые требования [WCAG 2.2 уровня AA](https://www.w3.org/TR/WCAG22/). Соответствие подтверждать проверками; автоматический сканер не доказывает его полностью.

### Вёрстка

- Mobile first, `<meta name="viewport" content="width=device-width, initial-scale=1">`.
- Проверять ширины 320, 360, 390, 768, 1024, 1440 и 1920 CSS px, а также промежуточные значения.
- Контейнер ограниченной ширины с гибкими боковыми отступами; типографика через `clamp()` с разумными пределами.
- Сетка карточек: одна колонка на телефоне, две на планшете, до трёх на широком экране. Границы выбирать по содержимому, а не конкретным моделям устройств.
- Не задавать фиксированную высоту текстовым секциям; длинные имена, цены и заголовки не должны ломать макет.
- Фото с заданным соотношением сторон; портрет кадрировать без обрезания лица.
- Нет горизонтальной прокрутки страницы при ширине 320 px. Проверить масштаб 200% и reflow при 400%.
- Фиксированная кнопка звонка допустима, если не перекрывает контент, фокус и подвал. Учесть safe area мобильных устройств.

### Доступность

- Семантические `header`, `nav`, `main`, `section`, `footer`; один `h1`, последовательная иерархия заголовков.
- Ссылка пропуска навигации; заметный фокус и полное управление клавиатурой.
- Ссылки — для переходов, кнопки — для действий. Иконки имеют понятные доступные названия.
- Контраст обычного текста минимум 4.5:1; крупного — 3:1; значимых графических элементов и границ контролов — 3:1.
- Минимум WCAG для целей нажатия учитывать вместе с исключениями; проектный ориентир кнопок — 44×44 CSS px и достаточные промежутки.
- Осмысленные `alt` для содержательных фото, пустой `alt` для декоративных.
- Если есть диалог галереи: доступное имя, перевод фокуса внутрь, удержание фокуса, Escape, возврат фокуса к исходной кнопке.
- Скрытое меню не оставляет невидимые ссылки в порядке Tab; кнопка имеет `aria-expanded`.
- Уважать `prefers-reduced-motion`; отключить необязательную анимацию. Контент не зависит от hover.
- При отключённом JS клиентский React не отрисует основной интерфейс. В `index.html` предусмотреть `noscript` с именем, телефоном и объяснением необходимости JS. Полная работа страницы без JS не входит в базовый CSR-вариант.
- Проверить NVDA или VoiceOver вручную хотя бы для основных сценариев.

## 7. Скорость и изображения

Цели по [Core Web Vitals](https://web.dev/articles/vitals): LCP ≤ 2.5 с, INP ≤ 200 мс, CLS ≤ 0.1 на 75-м процентиле реальных посещений. До появления достаточной статистики использовать лабораторные измерения как предварительную оценку, а не как доказательство полевых показателей.

Проектные бюджеты первой версии:

- JavaScript первого экрана, включая React, — желательно до 120 КБ gzip; если интерактивности почти нет, значительно меньше.
- CSS — ориентир до 40 КБ gzip.
- Первичная загрузка на мобильном — ориентир до 1 МБ; не скачивать полноразмерные фото всех объектов сразу.
- Lighthouse mobile: Performance желательно ≥ 90, остальные категории ≥ 95. Это вспомогательные пороги, а не сертификат качества.

Реализация:

1. Vite сам не создаёт адаптивные варианты изображений. Подготовить их заранее либо отдельным build-скриптом, например на Sharp: подходящие размеры, WebP/AVIF с совместимым вариантом, `srcset` и `sizes`.
2. Указывать `width`/`height`, чтобы избежать скачков макета.
3. LCP-изображение не загружать лениво; при необходимости дать ему `fetchpriority="high"`. Остальные изображения ниже первого экрана — `loading="lazy"`.
4. Полные фото галереи подгружать по необходимости. Удалять EXIF, включая GPS; хранить исходники приватно, если в них есть лишние сведения.
5. Использовать системный шрифт либо локальный WOFF2 с поддержкой кириллицы и `font-display: swap`. Не подключать внешние шрифтовые сервисы без необходимости.
6. CSS и JS — минифицированные файлы с хешами имён; Brotli/Zstandard/gzip — по возможностям сервера и клиентов.
7. Не добавлять тяжёлую UI-библиотеку, автопрокрутку, видеофон, карту iframe и сторонние виджеты ради декоративного эффекта.
8. На публичных хешированных ресурсах использовать долгий immutable-кеш; HTML и ресурсы с постоянными именами должны обновляться предсказуемо.

## 8. SEO и продвижение

- В базовом React CSR основной текст и карточки появляются после выполнения JavaScript. Поисковая индексация зависит от возможностей робота и не гарантируется фактом успешной сборки.
- Основные `title`, description, canonical, Open Graph и JSON-LD разместить непосредственно в `index.html` (при необходимости подставлять из общего конфига при сборке), чтобы они были доступны без запуска React, в том числе роботам мессенджеров.
- После публикации проверить отрендеренную страницу в инструментах поисковых систем. Если органическое продвижение станет главным каналом, отдельно согласовать build-time prerender одной страницы; это возможно без сервера в production, но в базовый простой вариант не включено.
- `lang="ru"`, осмысленные `title`, description, один `h1`, корректные метаданные Open Graph, favicon.
- Абсолютный canonical на основной HTTPS-домен; www/без www привести к одному варианту перенаправлением.
- `robots.txt` и sitemap с каноническими URL. Для одностраничника sitemap может содержать только главную; якоря не являются отдельными страницами.
- JSON-LD с правдивыми данными специалиста/бизнеса; подходящий тип Schema.org выбирать по реально публикуемым данным. Не добавлять вымышленные рейтинги, отзывы и адрес офиса.
- Встроенный JSON-LD согласовать с CSP через hash; не ослаблять всю политику ради одного блока.
- В тексте естественно упомянуть Чебоксары, Новочебоксарск, Чувашию и дистанционную помощь для Москвы/МО.
- Не создавать ложное впечатление офиса или личных показов в Москве.
- Настоящий HTTP 404 для несуществующих адресов; не перенаправлять все URL на главную как в SPA.
- После запуска подключить Яндекс Вебмастер и при необходимости Google Search Console, проверить индексацию и отображение ссылок.

Один лендинг может продвигаться по нескольким запросам, но не гарантирует высокие позиции одновременно по всем городам и услугам. Отдельные посадочные страницы — возможное последующее расширение, а не условие первой версии.

Аналитика не обязательна для запуска. Если она понадобится для рекламы, отдельно выбрать сервис, цели клика по звонку/мессенджеру, режим cookies и условия обработки данных. Нажатие на телефон — событие интереса, оно не доказывает состоявшийся звонок.

## 9. Безопасность приложения и браузера

Ориентир — применимые меры [OWASP ASVS 5.0](https://asvs.owasp.org/), без заявления о полной сертификации. Отсутствие базы и API уменьшает поверхность атаки, но остаются риски зависимостей, XSS через контент, подмены сборки, взлома хостинга и сторонних сервисов.

### Правила реализации

- В клиентском коде нет секретов. Всё, что включено в `dist/`, доступно посетителю.
- Не использовать `dangerouslySetInnerHTML`, `eval` и генерацию JS из текстового контента.
- Проверять внешние URL по схеме и ожидаемому домену; запрещать `javascript:` и неожиданные протоколы.
- Для ссылок в новую вкладку ставить `rel="noopener noreferrer"`, если передача referrer не нужна.
- Не публиковать `.env`, `.git`, исходные фотографии с чувствительными данными, архивы, ключи и локальные конфиги.
- Source maps не публиковать по умолчанию; они не должны содержать секретов даже в приватном окружении.
- Иконки/шрифты/скрипты хранить локально; по возможности исключить сторонний исполняемый JS.
- HTTPS везде; смешанного HTTP-контента нет.

### HTTP-заголовки

Настроить и проверить по фактическим ответам production-сервера:

- `Content-Security-Policy` с минимально необходимыми источниками.
- `X-Content-Type-Options: nosniff`.
- `Referrer-Policy: strict-origin-when-cross-origin` либо более строгая политика при отсутствии потребности передавать referrer.
- `Permissions-Policy` с запретом ненужных камеры, микрофона и геолокации.
- `frame-ancestors 'none'` в CSP; `X-Frame-Options: DENY` как дополнительная совместимость.
- HSTS включить после подтверждения стабильного HTTPS; `includeSubDomains` — только если все поддомены готовы. Preload не включать автоматически.

Стартовый профиль CSP для сайта с внешними локальными файлами JS/CSS: `default-src 'self'; script-src 'self'; style-src 'self'; img-src 'self'; font-src 'self'; connect-src 'none'; object-src 'none'; base-uri 'none'; frame-ancestors 'none'; form-action 'none'`.

Это проектный шаблон, не готовая универсальная настройка: проверить сборку Vite/React на inline-скрипты, inline-стили, data URL и JSON-LD. Вынести встроенный код в файлы либо добавить точные build-time hashes. Не устранять ошибки добавлением `unsafe-inline`/`unsafe-eval` ко всей странице. При подключении аналитики политику пересмотреть по конкретным запросам. Сначала проверить CSP в staging/Report-Only; `frame-ancestors` контролировать также в enforcing-политике, Report-Only не блокирует встраивание.

См. [руководство CSP](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/CSP) и [заголовки Caddy](https://caddyserver.com/docs/caddyfile/directives/header).

## 10. Персональные данные и внешние сервисы

В базовой версии нет формы, регистрации и собственной базы заявок. Не собирать паспортные данные, документы и сведения об ипотеке на сайте. Ссылки на мессенджеры не означают, что вся обработка данных отсутствует: остаются серверные access logs, возможная аналитика и последующее общение с клиентом.

Перед запуском владелец должен определить:

1. Кто выступает владельцем сайта/оператором и какие сведения о нём публикуются.
2. Какие данные фактически собираются хостингом, логами и аналитикой, зачем и на какой срок.
3. Нужны ли для выбранной схемы политика обработки данных, уведомления регулятору, согласия и иные документы.
4. Разрешено ли размещение выбранных фото, адресов и материалов собственников. Не раскрывать ФИО владельцев квартир и номера документов.
5. При подключении формы или внешних обработчиков — требования к локализации данных граждан РФ и трансграничной передаче.

Это вопросы к проверке по действующим нормам РФ перед публикацией, а не готовое юридическое заключение. Официальные точки проверки: [портал персональных данных Роскомнадзора](https://pd.rkn.gov.ru/) и [официальное опубликование правовых актов](https://pravo.gov.ru/). Портал РКН при подготовке плана не удалось загрузить, поэтому конкретные обязанности для владельца здесь не объявляются установленными.

Не добавлять формальную cookie-плашку автоматически. Сначала инвентаризировать cookies/трекеры; для необязательной аналитики предусмотреть механизм согласия, если он требуется по выбранному основанию. Документы должны соответствовать реальной работе сайта. При необходимости их можно разместить статическими файлами или дополнительными служебными HTML-страницами, сохранив одностраничную структуру основного сайта.

## 11. Docker и размещение на VPS

### Архитектура

```text
Исходники + фото → npm ci → проверки → Vite build → dist/
                                                        ↓
                                              Docker image с Caddy
                                                        ↓
                                               HTTPS → посетитель
```

Один production-контейнер раздаёт готовые файлы. Никаких Node-процессов, базы, Redis и backend в production не требуется. [Docker Compose поддерживает размещение на одном сервере](https://docs.docker.com/compose/how-tos/production/); [Caddy автоматизирует выпуск и обновление HTTPS-сертификатов](https://caddyserver.com/docs/automatic-https).

### Требования к Dockerfile

1. Multi-stage: Node для сборки, Caddy для исполнения.
2. Сначала копировать package-файлы и выполнять `npm ci`, затем исходники, подготовку изображений и сборку.
3. В финальный образ копировать только `dist/` и Caddyfile. Не переносить `node_modules`, инструменты разработки и репозиторий.
4. Запускать Caddy непривилегированным пользователем на внутренних портах 8080/8443; явно согласовать эти порты с автоматическим HTTPS и внешними 80/443.
5. Установить корректные права записи только для `/data` и `/config`, необходимые Caddy; остальная файловая система по возможности read-only. При необходимости выделить tmpfs для временных файлов.
6. Исключить из build context `.git`, `.env*` с секретами, `node_modules`, локальный `dist`, архивы и редакторские файлы. `.env.example` можно включать намеренно.
7. Проверять выбранную конфигурацию непривилегированного запуска на реальном образе, а не считать наличие `USER` достаточным доказательством.

### Требования к compose.yaml

- Один сервис `web`; публичные порты 80/tcp и 443/tcp. 443/udp — только если включён HTTP/3.
- Постоянные volumes Caddy для сертификатов и состояния; их владельцы и доступ проверены.
- `restart: unless-stopped`, ограничения памяти/CPU и ротация Docker-логов.
- `cap_drop: [ALL]`, `security_opt: [no-new-privileges:true]`; слушать непривилегированные внутренние порты.
- Не включать `privileged`, host networking, Docker socket или доступ ко всему диску хоста.
- Healthcheck на локальный `/health.txt`, с утилитой, которая действительно присутствует в финальном образе.
- Успешный healthcheck не гарантирует рабочий внешний DNS/TLS; необходима отдельная внешняя проверка. Статус unhealthy сам по себе не заставляет Compose перезапустить контейнер.
- Если на VPS уже есть reverse proxy, раздавать статику за ним по внутренней сети; не занимать повторно 80/443 и не выпускать сертификаты в двух местах без необходимости.

### Caddyfile

- Домен задаётся явно; http → https, один канонический hostname.
- Root — только каталог с собранным сайтом, directory browsing выключен.
- Сжатие, безопасные заголовки, правила кеширования.
- Хешированные ресурсы `/assets/*`: `public, max-age=31536000, immutable`, если все файлы по этому пути действительно имеют уникальные имена.
- HTML и файлы с постоянными именами: короткий кеш/revalidation, без годового immutable.
- Ошибки 404 возвращают код 404. Нет общего SPA fallback на `index.html`.
- Скрытые файлы, служебные пути и ненужные методы не доступны.
- Конфигурацию проверять `caddy validate` перед публикацией.

### Требования к хостингу

Обычный Linux VPS с поддерживаемой ОС, Docker Engine и Compose v2. Стартовый ориентир для раздачи статики — 1 vCPU и 512 МБ–1 ГБ RAM, но сборку лучше выполнять локально/в CI; изображения и инструменты сборки могут потребовать заметно больше памяти. Это оценка для небольшого трафика, а не гарантия производительности.

Открыть только 80/443 и ограниченный SSH. Проверить опубликованные Docker-порты снаружи: правила Docker могут взаимодействовать с firewall иначе, чем ожидается. SSH по ключам, доступ администратора ограничен, ОС обновляется; доступ к группе Docker фактически даёт высокие привилегии.

Домен должен указывать A/AAAA на доступный сервер; не публиковать AAAA при неработающем IPv6. Доступность порта 80/443, DNS и постоянное состояние Caddy проверить до ожидания автоматического выпуска сертификата.

## 12. Публикация, обновление и откат

### Первая публикация

1. Получить контакты, домен, фотографии и тексты, сверить список объектов.
2. Собрать сайт локально, выполнить проверки раздела 14.
3. Создать production-образ, пометить неизменяемым тегом commit SHA. Зафиксировать digest.
4. На VPS установить Docker/Compose, настроить DNS, firewall и каталоги/volumes.
5. Передать Compose/Caddy-конфигурацию без секретов. При использовании registry аутентифицироваться с минимально нужными правами.
6. Проверить `docker compose config`, затем получить образ и запустить сервис.
7. Проверить HTTPS, редиректы, headers, 404, контакты, изображения и мобильную версию через публичный домен.
8. Зафиксировать версию выпуска и сохранить предыдущий образ для отката.

В README реализации должны появиться точные команды, соответствующие созданным файлам. Предполагаемый процесс после появления конфигурации:

```sh
npm ci
npm run check
npm run lint
npm run build
npm run test:e2e

docker compose config
docker compose pull
docker compose up -d
docker compose ps
```

Для локальной сборки образа вместо pull используется `docker compose build`, если compose содержит `build:`. Не смешивать эти способы неявно: основной production-путь — заранее собранный образ; локальная сборка допустима как запасной путь. Не выдавать dev-сервер наружу.

### Обновление контента

1. Изменить `src/data/site.ts`, `services.ts`, `properties.ts` или фотографии.
2. Проверить карточки и контакты локально. Для снятия объекта поменять `published`.
3. Сделать commit; CI проверит типы, сборку и сценарии.
4. Собрать и опубликовать новый образ; заменить версию на VPS.
5. Проверить главную страницу и изменённые объекты; убедиться, что посетитель получает новый HTML.

Для обновления домена изменить одновременно build-time canonical origin, DNS и конфигурацию сервера. Runtime env не меняет уже встроенные значения в статическом HTML.

### Откат

Указать предыдущий тег/digest образа и повторить запуск сервиса. Данные мигрировать не требуется. Проверить, что старые ресурсы соответствуют HTML. При замене контейнера посетитель с ранее открытой страницей может запросить старый хешированный JS: при необходимости хранить ресурсы предыдущего выпуска в текущем образе или обеспечить короткое окно совместимости.

На одном VPS с одним контейнером возможна короткая пауза при пересоздании; нулевой простой не обещать. При реальной необходимости позднее добавить rolling/blue-green публикацию, но для первого выпуска она не обязательна.

## 13. Резервирование и сопровождение

- Git-репозиторий с удалённой копией — история исходников. Дополнительно хранить исходные фото, если они не входят в Git.
- Сохранять Compose, Caddyfile, инструкцию запуска и список DNS-записей.
- Хранить хотя бы несколько предыдущих образов и соответствующие lockfile/commit.
- Резервировать данные Caddy при необходимости; утерянные сертификаты можно перевыпустить, но учитывать лимиты центра сертификации.
- Не считать Docker volume резервной копией.
- Проверить восстановление сайта на чистом окружении: образ/исходники → настройка домена → запуск → доступный HTTPS. Для репетиции использовать тестовый домен и тестовую CA, если многократный выпуск сертификатов не нужен.
- Целевой ориентир восстановления — до 1 часа при наличии сервера, DNS-доступа и сохранённых артефактов; измерить на репетиции.
- Ежемесячно проверять зависимости, базовый образ, свободное место, сроки оплаты домена/VPS, контактные ссылки и актуальность объектов.
- Срочные уязвимости исправлять по риску, не дожидаясь месяца. Проверка `npm audit` дополняется сканером итогового образа, например Trivy.
- Access logs минимизировать, ограничить срок хранения и не записывать лишние query-параметры с данными посетителей. Организовать ротацию.
- По желанию добавить внешний uptime-monitor для HTTPS и главной страницы. Доступность мессенджера не контролируется сайтом.

## 14. Проверки и критерии приёмки

### Автоматически

- Установка из lockfile в чистом окружении, typecheck, lint и production build проходят.
- Проверка контента ловит дубли ID, отсутствующие изображения, пустые обязательные контакты и неверные URL.
- Playwright проверяет загрузку страницы, переходы по якорям, мобильное меню, галерею при наличии и корректные `href` контактов. Реальные звонки и сообщения тест не отправляет.
- axe-core не находит критических/серьёзных ошибок на главной и в открытых интерактивных состояниях.
- Проверены главная 200, неизвестный путь 404, HTTP→HTTPS и канонический редирект, актуальные headers, отсутствие публичных служебных файлов.
- Сканы зависимостей/образа не содержат необработанных применимых критических и высоких уязвимостей; исключения документируются с причиной и сроком устранения.

### Вручную

- Проверить реальные Chrome/Firefox/Safari/Edge поддерживаемых версий; отдельно Safari на iOS и Chrome на Android. Не ограничиваться эмуляцией viewport.
- Проверить ширины и масштаб из раздела 6, портретную/альбомную ориентацию, длинные тексты и медленную сеть.
- Пройти страницу клавиатурой и экранным диктором; проверить контраст, фокус, меню и диалог.
- При отключённом JS показан `noscript` с именем и телефоном; при включённом JS весь интерфейс отрисовывается без ошибок. Полная версия без JS не обещается.
- Все цены, фото, имена, география и часы соответствуют согласованным данным.
- Позвонить по ссылке с телефона и проверить переходы в фактически используемые мессенджеры. Не заявлять универсальную поддержку предзаполнения сообщений.
- Проверить production CSP без ошибок, влияющих на функциональность; проверить JSON-LD и метаданные.
- Измерить производительность на production-сборке, не на dev-сервере; записать условия измерения.
- Выполнить пробный откат и восстановление по README.

Результат приёмки — короткий отчёт с версиями браузеров, ссылкой/commit выпуска, результатами проверок и известными ограничениями. Написанные в этом плане проверки ещё не являются выполненными: их выполняют при разработке сайта.

## 17. Итоговые артефакты разработки

1. Исходники сайта на TS с вынесенным контентом и локальными ресурсами.
2. Lockfile и зафиксированная среда сборки.
3. Готовый статический `dist/`, не зависящий от Node.js на хостинге.
4. Dockerfile, compose.yaml, Caddyfile и `.dockerignore`.
5. README: локальный запуск, редактирование контента, сборка, Docker, DNS/HTTPS, обновление, откат и восстановление.
6. Базовый CI с проверкой типов, линтером, сборкой и значимыми браузерными сценариями.
7. Отчёт приёмки с проверками адаптивности, доступности, безопасности и производительности.

Это план реализации, а не созданный сайт. Указанные технологии и стандарты выбраны под небольшой статический проект; требования не означают обещания абсолютной безопасности или автоматического соответствия всем возможным стандартам.
